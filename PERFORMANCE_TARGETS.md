## Metrics

Measured on **both sender and receiver** unless noted:

1. **CPU usage** — process-level, normalized to one core and to total machine.
2. **Resident memory** — working set / RSS; plus steady-state allocation rate.
3. **Glass-to-glass latency** — synthetic frame counter captured at both ends;
   mean and p99.
4. **Frame pacing** — jitter, dropped frames, duplicate frames.
5. **Bandwidth** — at equal subjective *and* measured quality (PSNR/SSIM vs
   source).
6. **Startup / connection time** and **reconnect time**.
7. **A/V sync error** in ms, including across multiple audio tracks.
8. **Failure behavior** — under loss, bandwidth limits and slow receivers.

## Methodology (planned; to be confirmed in `exp_000/FINDINGS.md`)

- Synthetic media only (deterministic counter/tone markers), generated by the
  harness — see [HARNESS.md](HARNESS.md).
- Dedicated run per scenario; warm-up of 10 s, measurement window of 60 s
  unless a scenario specifies otherwise.
- Run each scenario 5 times; report median with min/max. Outliers recorded,
  not silently dropped.
- CPU sampled at ≥10 Hz from the OS process API; allocations from the
  instrumented upstream build and from Wormhole's own counters.
- Network conditions applied by the harness proxy (delay, drop, bandwidth
  cap) so both implementations see identical conditions.
- Results written as CSV + JSON into `exp_NNN/` and summarized in
  `exp_NNN/FINDINGS.md`; the summary in PROGRESS.md links to those files.

## Wormhole targets (starting hypotheses)

| Metric | Hypothesis target | Status |
|---|---|---|
| CPU vs Teleport, equal quality/resolution | ≥50% lower | unvalidated |
| Resident memory vs Teleport | ≥50% lower | unvalidated |
| Steady-state heap allocations on hot path | zero | unvalidated |
| Latency in low-latency profile | no more than one frame of buffering beyond baseline | unvalidated |
| OBS render-thread stalls attributable to plugin | zero | unvalidated |
| A/V sync error, all tracks | <10 ms | unvalidated |
| Behavior under every harness failure | graceful degradation (no crash/freeze) | unvalidated |

A target is promoted from `unvalidated` to `confirmed` only when a linked
result file in an `exp_NNN/` folder supports it, and both the baseline and the
measurement method are documented. If a target is shown to be unrealistic or
irrelevant, replace it (do not silently drop it) with an evidence-backed
value and log the change.

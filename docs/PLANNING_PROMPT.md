## Prompt

You are planning the next phase of **Wormhole**, an all-C OBS 33 plugin that streams a gaming PC's OBS output to a streaming PC over the LAN. Read the repository documents first: `GOAL.md`, `ROADMAP.md`, `PROGRESS.md`, `ARCHITECTURE_LOG.md`, `PROTOCOL.md`, `PERFORMANCE_TARGETS.md`, `HARNESS.md`, `RISKS.md`, and the experiment write-ups in `exp_014/` through `exp_017/`. Do not start editing code — produce a plan first.

### The user's vision (verbatim intent)

> Tie the output from the gaming PC to the streaming PC, so there is just **one video signal**, and match the output audios to the same as the output of the gaming PC, but send them with **different audio network channels**. If the UI is the same on both, that unlocks scene sync — we'll be able to switch scenes and mute/hide sources like a wormhole.

In other words: the streaming PC's OBS should look and behave like a **mirror of the gaming PC's OBS**, not like a separate machine with one receiver source. Video is one composited program feed; audio arrives as several independent network channels corresponding to the gaming PC's output tracks; scene collection, source names, visibility and mute state are synchronized so an action on one side is reflected on the other.

### What already exists (do not reimplement)

- `plugin/src/plugin.c` — module entry, Tools menu (`Wormhole...`), settings persistence in `plugin_config/wormhole/wormhole.json`.
- `plugin/src/output.c` — sender output on TCP 18090, v2 negotiation, HELLO_ACK carries sender name, SIMD JPEG video, bounded queues, idempotent stop, `obs_output_end_data_capture()` on stop.
- `plugin/src/source.c` — receiver source, auto-reconnect, libobs color parameters, discovery-aware properties, `WH2_MSG_SCENE_MANIFEST` application, automatic `wormhole-audio` clones.
- `plugin/src/audio_source.c` logic lives inside `source.c` — the `wormhole-audio` source type.
- `plugin/src/control.c` — sender settings control source with cyberpunk-styled properties, `PRINT STATUS TO LOG` reports `obs_video_active`.
- `plugin/src/discovery.c` — UDP 18092 LAN discovery with named peers.
- `plugin/src/transport.c`, `plugin/src/media.c` — sockets and libjpeg-turbo helpers.
- `core/c/protocol_v2.c`, `include/wormhole/protocol_v2.h` — v2 framing: HELLO, HELLO_ACK, STREAM_DESC, VIDEO, AUDIO, PING, GOODBYE, and the new `SCENE_REQUEST`/`SCENE_MANIFEST` text messages.
- Per-source audio is already captured pre-mix with `obs_source_add_audio_capture_callback()` and sent as independently named streams; the receiver already creates a `WH <source name>` audio clone per stream descriptor.
- A line-based scene manifest (`S:<scene>` / `I:<source>:<audio|video>`) is already generated by the sender after negotiation and applied by the receiver on the UI thread.
- Exp_016 fixed the crash on disable and the greyed-out Output Mode; preserve those invariants. Exp_017 introduced per-source audio and clone creation.

### Known gaps to solve

1. **Audio channel model is source-based, not output-track-based.** The user wants the receiver's audio channels to match the *gaming PC's OBS output tracks* (Simple/Advanced output mixers), each sent as a separate network channel. Decide whether to keep per-source capture and mix into output tracks on the sender, or migrate to `raw_audio2` mixer tracks with explicit track names, or support both. Some WASAPI output-capture sources in the test setup did not fire capture callbacks because of OBS monitoring-dedup logic — the design must still show every source in the UI.
2. **Scene manifest only copies scene names and item names/kinds.** It does not copy transforms, visibility, enabled state, source settings, scene order, or the active scene, and there is no ongoing control channel for scene switching / mute / hide updates.
3. **Video is one composited program feed.** The user explicitly wants just one video signal, so keep that; do not attempt per-source video.
4. No authentication on discovery/media; LAN only.

### What I need from you

Produce a **phased implementation plan** with:

1. **Architecture**: the exact data flow for (a) one video signal, (b) N audio network channels matching the sender's output tracks, (c) a scene/control channel carrying scene list, source list, visibility, mute and active-scene changes. Specify which side initiates, which thread each OBS API call must run on, and how to keep network work off OBS's render/audio threads.
2. **Protocol extensions**: concrete v2 message types and payload layouts, including a capability bit for scene sync, track-to-channel mapping, and control events (scene switch, mute toggle, visibility toggle). Keep backward compatibility with existing receivers/senders.
3. **OBS API research**: verify with the local OBS 33 headers/source in `third_party/obs-sdk/obs-studio-33.0.0/` — especially `obs_frontend_get_scenes`, `obs_scene_enum_items`, `obs_sceneitem_set_visible`, `obs_source_muted`/`obs_source_set_muted`, `obs_frontend_set_current_scene`, `obs_source_add_audio_capture_callback`, `obs_output_set_mixers`, `raw_audio2`, and `obs_queue_task(OBS_TASK_UI, ...)`. Cite file/line evidence.
4. **UI design**: how the receiver presents the mirrored scene collection and how the sender's Tools menu exposes sync/control, staying pure C (OBS properties API, no Qt). Keep the existing cyberpunk styling.
5. **Failure modes and invariants**: no crash on disable, no double stop, `obs_video_active()` must return to 0 when disabled, receiver reconnect, stale clone cleanup, refcount discipline (`bzalloc`/`bfree`), socket `shutdown()` before close, and no blocking calls on OBS threads.
6. **Test/evidence plan**: what to measure with the harness and the two portable OBS instances, which log lines prove each claim, and what goes into `exp_018/HYPOTHESIS.md` and `exp_018/FINDINGS.md`.
7. **Risks and open decisions** that need the user's input, called out explicitly.

Constraints: implementation must remain **all C**, build with MSVC `/W4 /WX` via `scripts/build_plugin.bat`, keep the C harness green on Windows/Linux/macOS, and follow the working loop in `AGENTS.md` (hypothesis first, short-lived branch, evidence, docs updated in the same commit series, PR with CI green). Do not claim parity or performance gains without linked evidence.

End your response with the single highest-priority first step.
